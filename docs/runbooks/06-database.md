# 06 — Database

The api's PostgreSQL: how its schema changes, how it is backed up, how to put
a backup back, and how to reach it from a laptop. Every command here was run
against staging on 2026-09-18 and its output is quoted as it appeared.

## What it is

| | staging |
| --- | --- |
| Instance | Cloud SQL `reward-api-db-staging`, PostgreSQL 16, `db-f1-micro`, zonal, 10 GB SSD with autoresize |
| Connection name | `helpme-reward-staging:us-central1:reward-api-db-staging` |
| Database, user | `reward`, `api` |
| Network | Public IP, no authorised networks, `ENCRYPTED_ONLY`. Nothing connects directly: Cloud Run and the proxy below go through the Cloud SQL connector, authenticated by IAM. |
| Password | Generated by Pulumi, never typed by a person; lives in the stack state (KMS-encrypted) and inside the secret |
| Secret | `reward-api-database-url-staging`: the whole `DATABASE_URL`, `postgres://api:…@/reward?host=/cloudsql/<connection name>/.s.PGSQL.5432&sslmode=disable` |
| Who can read it | the api's runtime identity `reward-api-run-staging@…`, and project owners |
| Backups | nightly from 03:00 UTC, seven retained, point-in-time recovery off |

Two tables so far: `schema_migrations`, which the runner owns, and `devices`.

## Migrations

The schema is `services/api/migrations/*.sql`, numbered, applied once each in
order by the runner in `services/api/lib/migrate.dart` and recorded in
`schema_migrations`. Each file runs in its own transaction with its row, so a
file that fails leaves nothing behind and is retried next time. There are no
down migrations: a mistake is corrected by the next numbered file.

On staging the runner is a Cloud Run job, `reward-api-migrate`, on the same
image as the service with `/migrate` as its command. `cd-api.yml` points it at
the new image and runs it before the service moves, so **you normally never
run migrations by hand**; you merge a file and the next deploy applies it. To
run the job yourself, for instance after a restore:

```sh
$ gcloud run jobs execute reward-api-migrate --region us-central1 --wait
Creating execution...
Provisioning resources...done
Starting execution...done
Running execution...done
Done.
Execution [reward-api-migrate-tn8jp] has successfully completed.
```

`--wait` makes the job's exit code yours. Its output is in the job's log, one
line per file applied:

```sh
$ gcloud logging read 'resource.type="cloud_run_job" AND resource.labels.job_name="reward-api-migrate"' \
    --limit 5 --format='value(textPayload)'
Container called exit(0).
schema is current; nothing to apply
```

A first run prints `applied 1 init` and `applied 2 devices` instead.

### Writing one

The next number, a short snake-case name, plain SQL: `0003_add_locale.sql`.
Only additive changes while any revision that might still serve reads the
old shape ([02](02-routine-change.md#changing-the-api-or-its-schema),
[04](04-rollback.md)). Test it locally against `docker compose` before the
pull request; the api's integration tests run the real directory and refuse
a duplicate number.

### A migration went wrong

If the **job failed**, nothing applied from that file and the deploy stopped:
fix the SQL in the same file and merge; the job retries it.

If the file **applied and was wrong** (a column with the wrong type, an index
that locks the table), write the next file to correct it and merge; do not
edit the applied file, its number is already recorded and the runner will not
run it again. If the damage is to data rather than shape, restore a backup
(below) and then rerun the job so the schema is current again.

## Backups

Nightly automated backups are on and seven are kept. An on-demand backup
before anything risky is cheap and instant to start:

```sh
$ gcloud sql backups create --instance reward-api-db-staging --description 'before 0003'
.......done.
[https://sqladmin.googleapis.com/sql/v1beta4/projects/helpme-reward-staging/instances/reward-api-db-staging] backed up.

$ gcloud sql backups list --instance reward-api-db-staging
ID             TYPE       STATUS      WINDOW_START_TIME              DESCRIPTION
1789748422721  ON_DEMAND  SUCCESSFUL  2026-09-18T16:20:22.721+00:00  runbook 06 rehearsal
```

Backups live with the instance: `pulumi destroy` takes them too. For anything
that must survive the instance, export to a bucket instead
(`gcloud sql export sql`). Point-in-time recovery is off on staging to keep
the cost at the floor; turn it on for production before it holds anything
(`settings.backupConfiguration.pointInTimeRecoveryEnabled` in
`infra/index.ts`).

## Restoring

A restore replaces the whole instance's data with the backup and takes the
instance offline for a few minutes; the api answers 500 on database routes
until it is back. Do it deliberately, tell whoever is watching, and expect to
rerun the migration job afterwards if the backup predates a migration.

```sh
$ gcloud sql backups list --instance reward-api-db-staging     # pick the ID
$ gcloud sql backups restore 1789748422721 --restore-instance reward-api-db-staging --quiet
Restoring Cloud SQL instance...
...done.
Restored [https://sqladmin.googleapis.com/sql/v1beta4/projects/helpme-reward-staging/instances/reward-api-db-staging].
```

On staging that took fourteen minutes (16:22:50 to 16:36:30 UTC), most of it
with the instance unavailable, for a database holding two empty tables; the
time is the instance restart, not the data. **Verify** it is back and the
schema is what you expect:

```sh
$ gcloud sql instances describe reward-api-db-staging --format='value(state)'
RUNNABLE
$ gcloud run jobs execute reward-api-migrate --region us-central1 --wait
Execution [reward-api-migrate-g29sx] has successfully completed.
$ gcloud logging read 'resource.type="cloud_run_job" AND resource.labels.job_name="reward-api-migrate"' \
    --limit 2 --format='value(textPayload)'
Container called exit(0).
schema is current; nothing to apply
```

After a restore, `schema_migrations` says which migrations the backup knew
about; the job run above applies any newer files, and prints `applied N name`
for each instead of `schema is current`.

Restoring to a *different* instance (to inspect a backup without touching
the live one) is `--restore-instance <other>` on the same command, against an
instance you created first with the same PostgreSQL version.

## Connecting from a laptop

Nothing connects to the instance directly. The Cloud SQL Auth Proxy opens an
IAM-authenticated, encrypted tunnel and exposes a plain local port; whoever
runs it needs `cloudsql.client` on the project (an owner has it) and
application-default credentials.

```sh
$ brew install cloud-sql-proxy            # once
$ cloud-sql-proxy helpme-reward-staging:us-central1:reward-api-db-staging --port 5433 &
2026/09/18 12:22:17 Authorizing with Application Default Credentials
2026/09/18 12:22:17 [helpme-reward-staging:us-central1:reward-api-db-staging] Listening on 127.0.0.1:5433
2026/09/18 12:22:17 The proxy has started successfully and is ready for new connections!
```

The password is inside the secret. Take it from there rather than from
anyone's notes, and do not write it down; the shell variable dies with the
session:

```sh
$ PW=$(gcloud secrets versions access latest --secret reward-api-database-url-staging \
       | sed -E 's|^postgres://api:([^@]+)@.*|\1|')
```

Through the proxy the URL is an ordinary TCP one. `sslmode=disable` is right
here too: the proxy encrypts, and the local hop is loopback. The api's own
migrator makes a good first check that the tunnel, the user and the schema
agree:

```sh
$ cd services/api
$ DATABASE_URL="postgres://api:$PW@localhost:5433/reward?sslmode=disable" fvm dart run bin/migrate.dart
schema is current; nothing to apply
```

For SQL, `psql` from the `postgres:16` image rather than a local install;
inside Docker the laptop is `host.docker.internal`:

```sh
$ docker run --rm -it postgres:16 psql "postgres://api:$PW@host.docker.internal:5433/reward" \
    -c '\dt' -c 'select version, name, applied_at from schema_migrations order by version'
             List of relations
 Schema |       Name        | Type  | Owner
--------+-------------------+-------+-------
 public | devices           | table | api
 public | schema_migrations | table | api
(2 rows)

 version |  name   |          applied_at
---------+---------+-------------------------------
       1 | init    | 2026-09-18 15:52:30.609107+00
       2 | devices | 2026-09-18 15:52:30.625717+00
(2 rows)
```

Stop the proxy when you are done (`kill %1`). The `api` user owns the tables
and can do anything to them; there is no read-only user yet, so treat a
session here as production access even on staging.

## Making a catalogue admin

The catalogue admin api (`/v1/admin/catalog`, [README](README.md)) answers
only people with a row in `admins`, and no route grants one, so the first
admin is made here, by hand. The person must have signed in once, which is
what creates their `users` row. Through the proxy above:

```sh
$ docker run --rm -i postgres:16 psql "postgres://api:$PW@host.docker.internal:5433/reward" <<'SQL'
INSERT INTO admins (user_id) SELECT id FROM users WHERE email = 'someone@example.com';
SELECT u.email, a.created_at FROM admins a JOIN users u ON u.id = a.user_id;
SQL
```

`DELETE FROM admins WHERE user_id = …` takes it away again. Every publish is
recorded in `catalog_events` with the publisher's user id, so who changed the
terms is never a mystery.

## Locally, without Google Cloud

`services/api/docker-compose.yml` is the same PostgreSQL 16 on
`localhost:5432` as `reward:reward`, empty until you run the migrator:

```sh
$ cd services/api
$ docker compose up -d --wait
$ export DATABASE_URL='postgres://reward:reward@localhost:5432/reward?sslmode=disable'
$ fvm dart run bin/migrate.dart
$ fvm dart test
```

`docker compose down -v` throws the data away; without `-v` it survives.
