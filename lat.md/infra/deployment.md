# Deployment

`develop` is the integration branch. A pull request runs the quality gate; merging deploys what it touched, the api as a new Cloud Run revision or the site to Cloudflare Pages, and smoke-tests the live URL.

Infrastructure is Pulumi, and GitHub authenticates to Google with Workload Identity Federation, so no service-account key exists anywhere.

The runbooks in `docs/runbooks/` cover it end to end: initial deployment, routine changes, infrastructure changes, rollback, troubleshooting and the site's Cloudflare setup.

## Ownership rule

Pulumi owns the shape of the api service; CI owns which image runs. Getting this wrong causes a silent rollback of production.

Every deploy points Cloud Run at a new image digest. If Pulumi also managed the image, the next `pulumi up` would reset the service to whichever digest it last recorded, deploying old code as a side effect of an unrelated infrastructure change. So `infra/index.ts` declares `ignoreChanges` on the container image, and the first `pulumi up` uses a public placeholder image that CI replaces within minutes.

## Pipeline

Five workflows in `.github/workflows/`, with the quality gate defined once and called three times, and a tag-driven mobile release beside them.

- **`verify.yml`** is the gate: `npm ci` at the root, then typecheck and test through the workspace scripts, which cover the two Pulumi programs and the repository config suites in `infra/tests`; an `infra` job that runs `npm ci --workspace infra` and `tsc --noEmit`, then authenticates keylessly as the deployer and runs `pulumi preview` against the staging state, so a review sees the exact diff an infrastructure change would apply ([[infra-tests#Infrastructure config#Verify gate previews the Pulumi program with keyless credentials]]); a `dart` job that resolves the pub workspace, analyses it and runs the `packages/domain` tests ([[infra-tests#Infrastructure config#Verify gate analyses and tests the Dart workspace]]); a `flutter` job that analyses and tests `apps/mobile` ([[infra-tests#Infrastructure config#Verify gate analyses and tests the Flutter app]]); an `api` job that tests `services/api`, builds its image and smoke-tests `/health` ([[infra-tests#Infrastructure config#Verify gate builds and smoke-tests the api]]). The site has no job of its own: it is static files the config suites check ([[infra-tests#Infrastructure config#The site is plain HTML and CSS]]).
- **`ci.yml`** calls it on every pull request into `develop` or `main`. A new push cancels the previous run.
- **`cd.yml`** deploys the site ([[deployment#Site]]). It runs on push to `develop` or `main` and on manual dispatch, ignoring pushes confined to `services/api`, `packages/domain`, `apps/mobile` or the api pipeline, which do not change the site. It calls the gate *again* rather than trusting the PR's tick, because the merge commit is not the commit CI tested. Deploys never cancel in flight.
- **`cd-api.yml`** is the api's deploy, filtered to `services/api`, `packages/domain`, the workspace manifests and itself ([[infra-tests#Infrastructure config#Api CD workflow is path-filtered to the api and the domain]]). Same keyless trust and verify-again shape as `cd.yml`; it builds the image, and adds one step between push and deploy: it points the migration job at the new image and executes it with `--wait`, so a failing migration fails the deploy before any replica serves. The smoke test then reads `/health` and posts a device with a zone shaped like an IANA name that Postgres does not know, which is refused with a 400 only after the database answered and stores nothing ([[infra-tests#Infrastructure config#Api CD builds, migrates, deploys and smoke-tests]]). Its variables are `API_CLOUD_RUN_SERVICE` and `API_MIGRATION_JOB`, from the stack outputs of the same names.
- **`release-mobile.yml`** runs on a `v*` tag, in the `staging` environment, one job per platform ([[infra-tests#Infrastructure config#Release workflow runs on version tags in the environment]]). A `tag` job fails a hand-started run on any other ref before either platform builds ([[infra-tests#Infrastructure config#Release workflow refuses anything but a version tag]]). Both authenticate keylessly as the deployer and read the signing material from Secret Manager into the runner's temp directory by the `SECRET_<NAME>` ids on the environment; no `secrets.*` is referenced ([[infra-tests#Infrastructure config#Release workflow stores nothing in GitHub secrets]]). Android builds the signed bundle and `apps/mobile/scripts/play-upload.sh` drives the Play Developer API with a token minted as the Play publisher identity, because fastlane's `supply` wants a key file this project refuses to have. iOS compiles unsigned on a macOS runner and the `beta` lane of `apps/mobile/ios/fastlane/Fastfile` imports the certificate into a throwaway keychain, archives with manual signing and uploads with the App Store Connect API key, waiting for Apple's processing so a rejected build fails the run ([[infra-tests#Infrastructure config#Store uploads are scripted beside the app]]). The build name is the tag without `v` or pre-release suffix; the build number is the run number, so a rerun is a duplicate the store rejects rather than a second release. Runbook 07 is the procedure; runbook 08 sets up what it reads.

The image is tagged with the commit SHA, never `latest`, and deployed by digest rather than tag. A digest is the exact bytes that were tested a step ago, and naming it is what makes a rollback a one-line command.

### Smoke tests

A deploy reporting success only means Cloud Run accepted the revision or Pages the files. The smoke tests, run against the live URL after each deploy, assert it is actually served.

Api revisions are named `<service>-sha-<commit>-<run number>`, so a manual dispatch of a commit that is already live makes a new revision rather than failing `ALREADY_EXISTS` ([[infra-tests#Infrastructure config#CD revision names carry the run number]]).

For the site they check that `/` returns 200 and that a missing path returns 404 rather than the page ([[infra-tests#Infrastructure config#The site smoke test checks the page and a 404]]).

### Action runtimes

Every action the workflows use is pinned at a major whose own `action.yml` declares `node24`, so the runner never has to force-upgrade a `node20` action and print the deprecation warning ([[infra-tests#Infrastructure config#Every workflow action declares the Node 24 runtime]]).

The warning is per action, not per workflow: an action's `runs.using` is fixed by its author, and nothing in the workflow YAML (the `node-version` given to `setup-node` included) changes it. The only workflow-side override is `ACTIONS_ALLOW_USE_UNSECURE_NODE_VERSION`, which opts *back* into Node 20 and is not used here ([[infra-tests#Infrastructure config#Nobody opts back into Node 20]]).

The Pulumi CLI comes from `pulumi/actions` in install-only mode (no `command`), because `pulumi/setup-pulumi` still declares Node 12 and has not been committed to since 2021 ([[infra-tests#Infrastructure config#Pulumi CLI comes from the maintained action]]). `subosito/flutter-action` is composite and nests `actions/cache@v5`, so it needs no bump. Dependabot watches the `github-actions` ecosystem weekly with `chore(ci)` commit prefixes so the next deprecation arrives as a pull request ([[infra-tests#Infrastructure config#Dependabot watches the workflow actions]]).

## Site

The static site in `apps/site/public` is served by Cloudflare Pages, one project per stack whose production branch is the git branch that deploys to it.

`develop` deploys to `helpmereward-staging` at `staging.helpmereward.com`, `main` to `helpmereward` at the apex.

It is the placeholder for the app's companion site, which replaced the PWA in issue #174; its content is issue #261. Pages builds nothing: `cd.yml` uploads the directory with a pinned `wrangler pages deploy --branch <branch>`, so each deploy is its project's production deployment ([[infra-tests#Infrastructure config#CD deploys the site to Cloudflare Pages]]). The job runs in the GitHub environment named after the stack (`staging`, or `prod` for `main`) and reads `CLOUDFLARE_ACCOUNT_ID`, `PAGES_PROJECT` and `SITE_URL` from it. The Cloudflare token comes from Secret Manager, fetched keylessly as the deployer like the signing material, so no workflow references a GitHub secret. That token can only edit Pages; Pulumi's own, in stack config as `cloudflare:apiToken`, also edits DNS. Runbook 09 makes both.

`404.html` exists so a missing path is a 404: without it Pages treats the project as a single-page app and answers every path with `index.html`. A rollback is a pointer move to an earlier deployment in the dashboard (runbook 09).

## Cache rules

`apps/site/public/_headers` sends `Cache-Control: no-cache` on every path, because the file names are not fingerprinted and a deploy must show on the next visit.

## Security headers

`apps/site/public/_headers` also sets the security headers for `/*`, so every path carries them; Pages applies the file to its responses ([[infra-tests#Infrastructure config#Pages headers carry the security policy]]).

The Content Security Policy fits a static page: `script-src` and `connect-src` are `'none'`, styles and images are same-origin, and nothing may frame it.

## Infrastructure

`infra/index.ts` declares everything the api needs to be built by GitHub and served by Cloud Run, plus the site's Pages project, custom domain and record on Cloudflare.

For the api that is an image registry, the service, its database, jobs and identities, and a keyless trust path from this repository.

The stack name doubles as the environment (`staging`, `prod`).

Provider settings (`gcp:project`, `gcp:region`) and `githubRepo` live per stack in `infra/Pulumi.<stack>.yaml`. `Pulumi.yaml` declares only the project's own unprefixed keys, because Pulumi rejects a namespaced key declared at project level without a value. `Pulumi.staging.yaml` targets `helpme-reward-staging` and trusts `helpmebrands/reward-app`; the test in [[infra-tests#Infrastructure config]] pins both.

Secrets are encrypted with a Cloud KMS key: `Pulumi.staging.yaml` names it in `secretsprovider` (`gcpkms://…/keyRings/pulumi/cryptoKeys/staging`) and carries the stack's wrapped data key in `encryptedkey`, both safe to commit ([[infra-tests#Infrastructure config#Staging uses the KMS secrets provider]]). The key ring and key were created by hand with `gcloud kms` on 2026-09-18 before `pulumi stack change-secrets-provider`, because the key that guards the state cannot live in the state; a new environment repeats that bootstrap. The first secret is the api's database password, generated in the program and never typed by a human. Pulumi state lives in the versioned GCS bucket `gs://helpme-reward-staging-pulumi-state`, never on a laptop; the bucket and key are named in config (`stateBucket`, `secretsKey`) so the program can grant the deployer preview access to them. Runbook 01 step 2 is the only login procedure, so a second, competing copy of the state is never initialised.

- **APIs** are enabled explicitly and everything depends on them, because enabling is slow and eventually consistent. `disableOnDestroy: false` so tearing down the stack does not switch APIs off underneath anything else.
- **Artifact Registry** keeps the 30 most recent images (rollbacks need them) and deletes untagged images after seven days, so the registry does not grow and bill forever.
- **Cloud Run conventions.** The site's Cloud Run service `reward-app`, its runtime account and its domain mapping were removed in issue #174; the api keeps their shape. `deletionProtection` is on for the `prod` stack. A service is public through `invokerIamDisabled` rather than an `allUsers` invoker binding: the organisation's domain-restricted sharing policy rejects `allUsers` in any IAM policy, and skipping the invoker check on one service is narrower than a project-wide policy exception. The service-level `scaling` block the API reports back is in `ignoreChanges`, or every preview would propose removing it, and so are the `managed-by` and `commit-sha` labels, the template labels and the revision name the deploy action writes, or every refreshed `up` would roll a new revision to strip them. A template change is applied with `pulumi up --refresh`: the refresh records the live digest as the image input, and without it the ignored image would be sent back as the bootstrap placeholder, silently deploying it.
- **The database** is one Cloud SQL PostgreSQL 16 instance, `reward-api-db-<env>`, at the tier in `dbTier` (`db-f1-micro` by default, the smallest, raised with load), zonal, 10 GB with autoresize, nightly backups on. Public IP with no authorised networks and `ENCRYPTED_ONLY`: nothing connects directly; Cloud Run reaches it through the Cloud SQL connector, a unix socket the platform mounts, authenticated as the runtime identity. It holds the `reward` database and the `api` user, whose password is a `random.RandomPassword` known only to the state and to Secret Manager. Deletion protection follows the `prod` stack like the api service.
- **The database secret** `reward-api-database-url-<env>` in Secret Manager holds the whole `DATABASE_URL`, so the api reads one variable on Cloud Run exactly as it does against docker compose ([[api-architecture#Migrations]]). Its form is `postgres://api:<password>@/reward?host=/cloudsql/<connection name>/.s.PGSQL.5432&sslmode=disable`: an empty authority with the socket in `host`, the socket file named in full because the Dart driver connects to that path verbatim rather than appending the file name as libpq does, and TLS off because the connector already encrypts.
- **The api runtime identity** `reward-api-run-<env>` holds exactly `cloudsql.client` (grantable only project-wide) and `secretmanager.secretAccessor` on that one secret, so it never runs as the broadly privileged default compute account.
- **The api service** `reward-api`: bootstrap image ignored after the first `up`, 0 to `maxInstances` instances, 80 concurrent requests, CPU only in flight, TCP startup probe, public through `invokerIamDisabled` because the apps call it directly and the api does its own authorization. It runs on the second-generation execution environment, set explicitly on the service and the job, because on gen1 a Dart connect to the Cloud SQL unix socket stalls until the request timeout while gen2 connects at once ([[infra-tests#Infrastructure config#Api service runs on the gen2 execution environment]]). It runs as the api identity with the Cloud SQL connector mounted at `/cloudsql` and `DATABASE_URL` injected from the secret's `latest` version; it depends on the secret binding because Cloud Run checks at revision creation that the identity can read every secret it references ([[api-architecture#Entrypoint]]).
- **The migration job** `reward-api-migrate` is a Cloud Run job on the same image with `/migrate` as its command, the same identity, socket and secret, no retries and a ten-minute timeout. CD runs it before each deploy ([[api-architecture#Migrations]]); its image is CI's too.
- **The reminder job** `reward-api-remind` runs `/remind` the same way, with `FIREBASE_PROJECT_ID` too, and Cloud Scheduler job `reward-api-remind` starts it every 15 minutes as its own account `reward-api-sched-<env>`, which holds `run.invoker` on that job and nothing else. The api identity also holds `firebasecloudmessaging.admin`, so the job and the service send through FCM HTTP v1 with a metadata-server token and no key file ([[api-architecture#Reminder sender]]). CD moves the job to each new image; the deployer holds `run.developer` on it.
- **Keyless deploys.** A Workload Identity Pool trusts GitHub's OIDC issuer, with an attribute condition pinning the repository owner. Only workflows from the configured `githubRepo` may impersonate the deployer account, which holds `artifactregistry.writer` on the one repository and `run.developer` on the api service and both api jobs, plus `serviceAccountUser` on the api runtime account, which deploying a service that runs as another identity requires. No service-account key exists anywhere.
- **Previews from CI.** So the `infra` job can run `pulumi preview`, the deployer also holds three read-side roles: `viewer` on the project (read everywhere, and not secret payloads), `storage.objectUser` on the state bucket (a preview takes the state lock, which is an object write) and `cloudkms.cryptoKeyDecrypter` on the one secrets key (the state's secrets must decrypt to diff). None of these can apply a change: the deployer still cannot `pulumi up`.
- **This stack's GitHub environment.** Each environment stack owns one `github.RepositoryEnvironment` named after itself (`staging`) and writes onto it, as `github.ActionsEnvironmentVariable` resources, every value the workflows read: project, region, image repository, the api's service and job names, the workload identity provider, the deployer email and the site's Cloudflare account, Pages project and URL, fed from the resources directly. The deploy jobs and the preview job run in that environment, so `vars.X` resolves per stack and nothing is copied from `pulumi stack output` by hand ([[infra-tests#Infrastructure config#Every workflow variable is declared on the environment]]). None are secret: identifiers, readable in a failed deploy's log. GitHub creates an environment implicitly the first time a workflow names one, so one a deploy has already used is adopted with `pulumi import` (runbook 01 §5). Staging cut over from repository variables and a `develop` environment on 2026-09-20.
- **The develop ruleset** lives in the second program, `infra-repo/`, with exactly one stack, `repo`, on the same backend and key: what is true of the repository regardless of environment cannot be owned by an environment stack, or `staging` and `prod` would fight over it ([[infra-tests#Infrastructure config#Repo-level project has its own stack]]). It declares one `github.RepositoryRuleset` on `refs/heads/develop` requiring every job of `verify.yml` as a status check, by the `verify / <job name>` context each reports under, with the up-to-date policy on. The list is derived from the workflow file at program time by `infra-repo/verify-checks.ts` ([[infra-tests#Infrastructure config#Required checks derive from verify.yml]]), so adding a job requires it at once and renaming one is a ruleset diff; the pull request that renames a job is blocked until `pulumi up` runs from that branch (runbook 01 §6). Each check is pinned to GitHub Actions' app id so no other integration can satisfy it by name. The provider authenticates with `github:token`, a fine-grained token for this one repository held as secret config, or with `GITHUB_TOKEN` from the environment; the verify gate passes its own workflow token, which reads but cannot administer, enough for a preview that never refreshes. The pull-request-only rule is an organisation ruleset and is not repeated. The staging ruleset predates the program and was adopted with `pulumi import`.
- **Budget.** One `gcp.billing.Budget` of `budgetAmount` USD a month (default 25) filtered to the stack's project number, with threshold rules at 50, 90 and 100 percent of actual spend and 100 percent of forecast spend. No `allUpdatesRule`, because the provider then demands a notification channel or topic; the API default emails billing-account administrators and users instead. Budgets live on the billing account, so `billingAccount` is required config, held as a secret because the repository is public, and the operator applying the stack needs Billing Account Costs Manager on the account while the deployer, which only previews, needs nothing ([[infra-tests#Infrastructure config#Program declares the budget]]).
- **Mobile release trust.** The platform half of a store release, without the release logic: a Play publisher identity `reward-app-play-<env>` that this repository's workflows assume through the same workload identity pool as the deployer (Play Console links it by email, so no key file exists), and Secret Manager containers `reward-app-<name>-<env>` for the App Store Connect key, iOS certificate and profile and Android keystore with their passwords, plus the Cloudflare deploy token. The containers have no versions: values are added and rotated by hand (runbook 07), and the deployer holds `secretAccessor` on exactly these so a workflow fetches them at build time and GitHub stores nothing ([[infra-tests#Infrastructure config#Deployer reads exactly the signing secrets]]). The identity's email and every secret id are written onto the GitHub environment as `PLAY_SERVICE_ACCOUNT` and `SECRET_<NAME>`. The fastlane workflow that uses them is a separate change.
- **The api's custom domain** mapping is created only when configured, because it fails unless the domain has already been verified in Search Console by the account running `pulumi up`, a manual step. DNS for `helpmereward.com` is in Cloudflare, and the mapping's CNAME must stay DNS-only (unproxied) or Google's managed certificate never issues; runbook 03 has the procedure and the proxy caveats.
- **The site on Cloudflare** is a `cloudflare.PagesProject` named `pagesProject` with production branch `siteBranch`, a `PagesDomain` for `customDomain` and a proxied CNAME from it to the project's `pages.dev` subdomain; Cloudflare flattens it at the apex. They are left out until `cloudflareAccountId` and `cloudflareZoneId` are set, so a stack without Cloudflare access still previews ([[infra-tests#Infrastructure config#Pulumi declares the Pages project, its domain and its record]]).

Staging is project `helpme-reward-staging` in `us-central1`, stack `staging`, deployed from `develop`; the site is Pages project `helpmereward-staging` at <https://staging.helpmereward.com>. The apex `helpmereward.com` is reserved for `prod`. The table in `docs/runbooks/README.md` is the record; [[infra-tests#Infrastructure config]] pins it.

The stack outputs mirror the values the program writes onto the GitHub environment, for a human reading them back: `WIF_PROVIDER`, `DEPLOY_SERVICE_ACCOUNT`, `ARTIFACT_REPO`, `GCP_REGION`, `GCP_PROJECT_ID`; plus `API_CLOUD_RUN_SERVICE`, `API_MIGRATION_JOB` and `API_REMIND_JOB` for `cd-api.yml` ([[infra-tests#Infrastructure config#Stack outputs name the api service and job]]), and, for runbook 06, `apiServiceUrl`, `apiRuntimeServiceAccount`, `databaseInstanceConnectionName` and `databaseUrlSecretId`; for runbook 09, `pagesProject` and `pagesSubdomain`.
